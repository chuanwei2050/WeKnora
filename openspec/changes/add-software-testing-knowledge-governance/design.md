## Context

当前 `Knowledge` 记录保存来源、文件哈希、通用 metadata 和处理状态，手工知识只在 JSON metadata 中维护一个递增版本号；重新上传、同步或重新解析会更新同一知识，但没有不可变版本快照、审核记录和当前发布版本指针。`ExtractConfig` 已允许知识库配置实体与关系，可作为领域模型的承载入口，但需要用户从空白开始配置，也没有软件测评标准的版本与效力规则。

本变更面向知识管理员、领域审核人和问答用户。约束是继续支持 PostgreSQL/SQLite、现有数据源同步与异步索引，并保证未启用治理模式的知识库行为不变。

## Goals / Non-Goals

**Goals:**

- 提供版本化的软件测评领域知识模型和四层知识来源，并允许管理员在启用时调整。
- 以不可变版本、审核记录和原子发布指针管理知识生命周期。
- 只让已发布且有效的当前版本进入生产检索、图谱与引用。
- 保持旧知识库、现有 API 和异步处理链兼容。

**Non-Goals:**

- 不自动从互联网采购或更新标准全文。
- 不以模型评分替代领域人员对知识正确性的最终审核。
- 不在本变更中实现文档 DRM、密级管理或电子签章。

## Decisions

### 1. 知识身份与版本分离

保留现有 `knowledges` 作为稳定知识身份，新增 `knowledge_versions` 保存版本标签、文件/内容快照引用、哈希、来源元数据和单一生命周期状态，并在知识身份上保存 `current_version_id`。`chunks` 增加 `knowledge_version_id`。

生命周期使用可穷举枚举而不是审核、发布、有效等可互相矛盾的布尔字段：`draft → pending_review → approved → indexing → active`；未来生效版本走 `indexing → scheduled → active`；失败、驳回和退出生产分别进入 `publish_failed`、`rejected`、`superseded` 或 `expired`。只有状态机允许的迁移可以发生，API 中的“已审核”“已发布”“当前有效”等展示属性从该状态和 `current_version_id` 派生。回滚允许仍有效的 `superseded` 版本重新进入 `indexing`，成功切换后成为 `active`。

选择该方案而不是“每个版本一条 Knowledge”，因为分享、标签、会话引用和外部 API 均依赖稳定的 knowledge ID。版本记录不可原地修改；修订会生成新版本。

### 2. 治理模式按知识库显式启用

在知识库配置中增加 `governance.enabled` 与 `profile_id/profile_version`。未启用时继续执行现有即时入库流程；启用后，新内容先形成待审核版本，旧的已发布版本在新版本发布成功前继续服务。

这比全局强制审核更符合兼容性要求，也允许先在软件测评知识库试点。

### 3. 领域模型使用版本化配置文件

在仓库配置中维护 `software-testing` profile，包含概念、属性、关系、必填来源字段和稳定的知识层级枚举；启用时复制为知识库的可编辑快照，并记录 profile 版本。首版知识来源至少覆盖 `standard`（国家/行业标准）、`foundation`（基础理论）、`internal`（企业内部体系规范）和 `experience`（项目历史/专家经验），领域概念至少覆盖测评对象、质量特性、测试类型/方法、工具、指标、缺陷和结论。

选择配置驱动而不是硬编码 Go 枚举，便于领域专家评审后调整且不必改业务代码。

### 4. 发布采用“先构建、后切换”

`draft` 和 `pending_review` 版本可完成解析并生成未启用 chunk，但不写入生产向量、关键词和图谱索引。审核通过后状态进入 `approved`，异步任务切换为 `indexing` 并构建新版本索引；若版本已经生效，全部索引成功后在事务中切换 `current_version_id`、把新版本设为 `active` 并把旧版本设为 `superseded`。若 `effective_at` 位于未来，则索引成功后进入 `scheduled`，旧的 `active` 版本继续服务；定时激活任务到点后再执行原子切换。索引或切换失败进入 `publish_failed`，旧版本保持可用，重试时从 `publish_failed` 回到 `indexing`。

回滚复用同一切换流程，目标必须是历史上已审核通过的版本。

### 5. 来源效力参与检索可见性

发布条件要求知识层级、来源类别与领域 profile 的必填元数据完整。`scheduled` 版本在达到 `effective_at` 前、任何版本在超过 `expires_at` 后均不得作为当前有效证据；定时任务负责预约激活、到期和幂等重试。`active` 到期时，系统在同一原子操作中切换到已就绪且当前有效的 `scheduled` 后继版本，或在没有后继时把原版本设为 `expired` 并清空 `current_version_id`，不得留下指向非 `active` 版本的当前指针。若同一知识存在多个时间窗口重叠的已批准候选版本，服务层按明确规则拒绝进入 `indexing` 或要求管理员消除冲突，不静默选择。引用对象携带知识层级、标准编号、版本和生效信息。

### 6. 审核沿用知识库权限边界

首版由知识库管理员执行审核，编辑者可提交但不可批准自己的待审版本。审核记录单独持久化并只追加，服务层同时校验 tenant、knowledge base 权限和版本状态。

## 集成边界

- 本变更不依赖其他新增变更即可实施，是后续图谱证据版本化和评测知识快照的来源。
- `add-multihop-graph-retrieval` 若已启用，只消费本变更提供的 `knowledge_version_id` 和发布可见性，不重复实现版本规则。
- `add-verified-multi-agent-answering` 采纳的知识纠错反馈只能在本变更启用时创建新的治理草稿，不得直接修改已发布版本。
- `add-research-acceptance-benchmarks` 使用不可变版本或内容清单作为评测快照，不改变本变更的审核状态。

## Risks / Trade-offs

- [多检索引擎的版本切换难以完全事务化] → 采用可重试的发布状态机和幂等索引操作，数据库指针只在所有目标索引成功后切换。
- [领域 profile 首版不完整] → profile 明确版本号，允许知识库级扩展，并将最终 taxonomy 交由软件测评专家验收。
- [版本快照增加存储] → 内容哈希相同时不复制二进制对象，只复用对象引用并新增元数据快照。
- [失效版本导致召回骤降] → 在管理界面提前提示即将失效知识，不自动回退到已失效证据。

## Migration Plan

1. 增加治理配置、版本表、审核表、版本字段和索引，先部署为未启用状态。
2. 为现有知识按需创建兼容版本快照；未启用治理的知识库继续读取旧路径。
3. 在试点知识库启用 profile，补齐四层知识来源，校验现有元数据并由管理员确认初始发布版本。
4. 演练即时发布、未来预约生效和到期停用，再启用新检索过滤和引用字段。
5. 观察索引一致性后逐步扩大范围。
6. 回滚时关闭治理开关并继续使用原 knowledge/chunk 路径；数据库新增表保留，不做破坏性删除。

## Open Questions
