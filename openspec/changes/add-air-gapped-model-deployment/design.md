## Context

当前模型层已经具备可复用基础：`internal/models/chat` 和 `internal/models/embedding` 将 `source=local` 路由到 Ollama；`generic` 和 GPUStack provider 通过自定义 `base_url` 支持 OpenAI-compatible 的 Chat、Embedding、Rerank、VLM 和 ASR；Lite 模式可使用 SQLite、本地存储/内存组件和 Ollama，Docker Compose 与 Helm 可部署服务器组件。模型配置入口会调用 `ValidateURLForSSRF`，部署者可通过 `SSRF_WHITELIST` 批准内网端点。但桌面端现有自动更新流程会访问 GitHub，严格断网 profile 必须显式关闭该路径。

但现有语义和交付链仍不完整：`local` 实际等同于 Ollama 并会在缺少模型时尝试联网拉取；内网 OpenAI-compatible 服务仍被标记为 `remote`；不同模型类型的连接检查没有统一能力契约；ASR 只实现批量 OpenAI-compatible 接口，TTS 尚不存在；没有严格断网开关来阻止公共云回退、外部搜索、遥测或自动下载；Compose/Helm 中仍有浮动镜像标签，也没有可校验的离线介质和断网验收流程。

客户的约束是最终运行环境没有公网出口，全部模型和数据服务均在内网。为降低前六个业务变更的联调风险，本设计采用线上优先、离线最后替换，但要求业务代码从一开始只依赖模型能力接口，不依赖云厂商特有行为。

## Goals / Non-Goals

**Goals:**

- 用同一套模型能力契约先建立线上基线，再切换到内网模型并重复验收。
- 覆盖 Chat、Embedding、Rerank、VLM、ASR、TTS、验证/反思、评测裁判和可选解析/OCR 模型角色。
- 在严格离线模式下阻断隐藏公网依赖、运行时下载和公共云回退。
- 提供受控内网端点、部署预检、离线介质、配置迁移和回滚能力。
- 让桌面 Lite、Docker Compose 与 Helm 均可在预装制品和模型的无公网环境启动。

**Non-Goals:**

- 不在仓库中再分发许可证不允许分发的模型权重。
- 不实现 GPU 驱动、CUDA、推理框架本身的安装器。
- 不保证任意 OpenAI-compatible 服务自动具备工具调用、结构化输出或流式能力。
- 不为每个内网模型厂商复制一套业务流程。
- 不在本变更中重新实现前六个业务能力；只做模型和部署等价适配。

## Decisions

### 1. 以模型角色和能力为契约，而不是以厂商名分支

定义 `ModelCapabilityManifest`，记录模型角色、协议、运行位置、流式输出、工具调用、结构化输出、视觉输入、音频输入/输出、文档解析/OCR、最大上下文、Embedding 维度、并发限制和超时。角色至少覆盖 Chat、Embedding、Rerank、VLM、ASR、TTS、验证/反思和评测裁判，可选覆盖解析/OCR。VLM 是视觉语言模型角色，vLLM 只是可能承载一个或多个角色的推理服务引擎，两者不得作为同一枚举维度。智能体与业务流程声明所需能力，保存配置和运行预检时做匹配。

选择该方案是因为“OpenAI-compatible”只说明接口形状，不保证具体功能。替代方案是在业务代码中识别 Ollama、GPUStack、vLLM 等厂商，但这会让每个新增流程重复适配，难以验证线上与离线等价性。

### 2. 将接口协议、运行位置和获取策略分离

扩展模型配置，分别表达：

- `protocol`：`ollama`、`openai-compatible` 或已有专用协议。
- `location`：`public`、`private-network`、`same-host`。
- `artifact_policy`：`preloaded-only` 或允许下载。

现有 `source=local` 继续兼容映射为 `protocol=ollama` 与 `location=same-host`；`source=remote` 根据规范化端点、批准端点注册表和连接期 DNS/IP 解析结果迁移，不再把“远程 HTTP”误解为“公网模型”。`location` 是服务端分类结果而非普通用户可自报并绕过网络策略的信任字段。迁移期 API 保留旧字段，新的判断只依赖规范化配置和服务端判定。

### 3. 线上基线和内网切换使用显式门禁

阶段 A 使用批准的线上模型完成前六个变更，并冻结模型配置、评测套件、提示版本和运行报告。阶段 B 为每个模型角色绑定内网端点，执行能力预检和同一套回归；只有内网运行达到相同功能门禁以及项目定义的准确率、性能与并发门禁后才完成切换。

该顺序隔离“功能错误”和“本地模型适配错误”。离线结果不要求逐字等同线上回答，但必须通过同一冻结验收规则，失败差异要落入报告。

### 4. 内网依赖通过统一批准端点注册表放行

新增管理员维护的 `ApprovedEndpoint` 注册表，保存规范化 scheme、host、port、协议、TLS/证书策略、服务类别和允许用途。服务类别至少包含 `model`、`search`、`data-connector`、`object-storage` 和 `telemetry`；模型类别额外保存允许的模型角色，其他类别保存对应连接器或服务用途。业务配置只能引用用途匹配的批准端点，不能把已批准的 S3 地址当作模型端点或把遥测端点当作数据源。服务端根据注册表构建允许清单，并继续在每次连接及重定向时执行 DNS/IP 校验以防 DNS rebinding。普通租户不能通过提交任意 URL 扩大内网访问范围。

现有 `SSRF_WHITELIST` 继续作为部署级启动配置，但预检必须确认全部批准端点与白名单、服务类别和用途一致。直接关闭 SSRF 防护不是可接受方案；端点凭据仍通过独立 secret 机制保存，不进入注册表导出。

### 5. 严格离线模式采用默认拒绝策略

新增 `AIR_GAPPED_MODE=true`。启用后：

- 拒绝 `location=public` 的模型和未注册公网 URL。
- 禁用公共 Web Search、公共数据源同步、云端遥测和公网云对象存储配置；允许管理员在 `ApprovedEndpoint` 注册表按用途批准的内网搜索、数据连接器、S3 兼容存储和自托管遥测。
- 禁止 Ollama pull、镜像拉取辅助流程和其他运行时下载。
- 桌面 Lite profile 禁用 GitHub 自动更新检查及任何后台版本请求，改为离线介质驱动的人工升级。
- 未找到本地模型、镜像或资源时快速失败并报告缺项。
- 禁止从内网模型故障静默回退到公共云模型。

该开关在配置边界集中执行，业务纯逻辑不重复散布离线判断。管理员可以使用明确的开发模式关闭它，但生产断网验收必须开启。

### 6. 模型调用共享受控 HTTP 传输与健康检查

OpenAI-compatible Chat、Embedding、Rerank、VLM、ASR、TTS、验证/反思、评测裁判和可选解析/OCR 模型统一使用支持超时、取消、TLS、受控自定义 Header、SSRF 校验和连接池的传输工厂。每个角色实现最小功能探针，而不只检查 TCP 可达：Chat 验证流式/结构化/工具能力，Embedding 验证维度，Rerank 验证结果顺序，VLM 验证图像输入，ASR/TTS 验证音频接口，验证与评测裁判验证结构化评分，解析/OCR 验证选定文档或图像输入。

Ollama 保留原生客户端，但在 `preloaded-only` 下只检查模型存在，不执行 `PullModel`。

### 7. 离线介质由清单驱动并固定版本

增加离线打包命令，读取部署清单后导出桌面 Lite 制品、应用及依赖镜像、Helm Chart、Compose 配置、数据库迁移、前端静态资源和操作文档，生成 SHA-256 校验和、版本、架构和来源清单。正式离线 override/values lock 与介质清单必须固定镜像摘要或不可变版本且不得包含浮动 `latest`；通用开发 Compose/Helm 默认值不因本变更被强制改成客户环境版本。

模型清单记录名称、版本、推理协议、硬件要求、许可证、文件校验和和导入步骤。只有部署方确认可再分发时才把权重加入介质；否则把权重标为外部必备项并在预检中验证。

### 8. 三种离线部署 profile 复用同一门禁

- `desktop-lite`：桌面应用使用 Lite 支持的 SQLite、本地存储/内存组件以及同机或批准内网模型，关闭自动更新与公网依赖。应用、全部启用且必需的数据组件和全部必需模型端点均为 `same-host` 时执行并可声明 `single-node` 验收；若使用 `private-network` 模型，只能执行无公网功能与质量验证，`single-node` 门禁必须失败并列出非同机端点。
- `compose-airgap`：使用固定离线 override 和已导入的本地镜像启动服务器组件。
- `helm-airgap`：使用固定离线 values/lock 和内网镜像仓库启动服务器组件。

三个 profile 使用同一业务回归套件，但按验收变更定义分别应用 `single-node` 或 `server-load` 门禁，并分别记录不适用项。运行位置必须由服务端可信判定；不得仅因 Lite 不包含服务器集群依赖就宣称服务器并发验收通过，也不得把使用内网远程模型的桌面环境宣称为纯单节点。

### 9. 密钥和环境配置与介质分离

离线包不包含真实 API Key、数据库密码、JWT 密钥或证书私钥。Compose 使用 `.env`/secret file，Helm 使用 existing Secret；导入工具只提供模板和必填项校验。模型配置导出默认脱敏，导入后由管理员重新注入凭据。

### 10. 断网验收由部署预检和端到端测试组成

预检验证镜像、模型、端点、能力、向量维度、数据库迁移、存储、证书、资源和外部 URL。随后在网络层禁止公网出口，执行文档导入、索引、检索、回答、引用、复杂路由、验证、语音和验收基准的适用场景，并记录所有出站连接尝试。报告必须区分“不支持”“缺少资源”和“执行失败”。

## 集成边界

- 前六个业务变更定义模型角色所需能力和冻结回归，本变更只提供端点、离线策略、制品及等价性验证，不复制业务流程。
- 验收基准变更定义 `single-node`/`server-load` profile 和门禁计算，本变更提供应用、数据组件与模型端点的位置证据、对应部署环境、运行清单和出站审计。
- VLM、验证模型和评测裁判可以由同一推理引擎承载，但模型身份与能力仍按业务角色分别登记和预检。
- 管理员批准的内网模型、搜索、数据源、S3 和自托管遥测统一由 `ApprovedEndpoint` 按服务类别和用途治理；严格模式禁止的是未批准、用途不匹配或解析到公网的目标。

## Risks / Trade-offs

- [内网模型具备接口但能力不足] → 在切换前执行角色级功能探针，并允许为不同角色使用不同模型。
- [本地模型质量低于线上基线] → 使用同一冻结评测集量化差异，调整模型或硬件后重跑，不在业务代码中为通过门禁硬编码答案。
- [严格离线模式误伤必要内网服务] → 以内网端点注册表和显式网络策略区分内网与公网，并在启用前输出完整依赖图。
- [客户端自报 `private-network` 绕过限制] → 运行位置由服务端结合注册表和连接期解析判定，配置字段仅作展示结果。
- [已批准端点被跨用途滥用] → 注册表使用可穷举服务类别和用途约束，每个配置边界校验用途，连接审计同时记录端点与调用类别。
- [镜像或模型介质过大] → 清单按部署启用的组件裁剪，但不能省略运行时实际依赖。
- [模型许可证禁止打包] → 权重与应用介质解耦，清单记录许可和客户自行导入步骤。
- [旧 `source` 字段迁移歧义] → 保留兼容映射并要求管理员确认无法自动判定的私网端点，迁移可回滚。

## Migration Plan

1. 在现有线上配置上完成前六个变更并保存冻结回归基线。
2. 增加模型能力清单、规范化部署字段和旧配置兼容读取，默认不开启严格离线模式。
3. 统一模型 HTTP 传输、`ApprovedEndpoint` 注册和模型/搜索/数据/存储/遥测用途级连接检查。
4. 增加 `AIR_GAPPED_MODE`，先在联网测试环境中以出口审计方式演练，再切断公网。
5. 生成固定版本的桌面 Lite 制品、Compose 离线 override、Helm 离线 values/lock、离线介质和模型清单，不改写通用开发默认值。
6. 绑定内网模型，分别对 `desktop-lite`、`compose-airgap` 和 `helm-airgap` 执行适用预检、同套回归和断网端到端验收。
7. 切换失败时恢复上一份模型绑定和部署配置；数据库迁移保持向后兼容，旧 `source` 字段在一个迁移周期内保留。

## Open Questions

- 客户最终采用 Ollama、GPUStack、vLLM 还是其他 OpenAI-compatible 推理平台，需要根据 GPU 资源和模型许可确定。
- 各模型角色的具体模型、显存预算、并发配额和最大上下文需要在硬件清单确定后固化。
- 客户是否允许在内网部署自托管 Langfuse；若不允许，验收报告使用项目本地持久化能力。
