## Context

WeKnora 具有向量、关键词、结构化数据、知识图谱、Wiki 和 FAQ 等多种知识库检索路径。若在每个渠道内分别处理简称，改动面大且规则容易不一致，因此简称处理放在检索路由之前，形成轻量公共预处理步骤。

## Goals / Non-Goals

**Goals:**

- 在知识库设置中维护简单的“简称—标准名称”映射。
- 在任何知识库检索路由之前只处理一次查询，并让下游复用结果。
- 保留原始简称并追加标准名称，兼顾已有索引和标准名称内容。
- 无配置、未命中或读取失败时保持原有检索行为。

**Non-Goals:**

- 不训练或微调模型。
- 不设计通用实体、资质编码或复杂歧义工作流。
- 不修改已有 chunk、embedding、ES 索引、图谱节点、Wiki 页面或 FAQ 数据。
- 不在每个检索 driver 中重复读取简称配置。

## Decisions

### 1. 简称作为知识库 JSON 配置持久化

在 `knowledge_bases` 增加 JSON 字段，每项仅包含 `alias` 和 `standard_name`。第一版只需随知识库维护少量映射，不需要独立实体表或跨知识库关联。

服务端保存前清理首尾空白并校验空值、长度、条数及同一知识库内规范化后的简称重复；前端校验只用于即时提示，服务端是最终边界。

### 2. 在检索路由前统一扩展查询

公共能力接收原始查询及当前授权知识库范围内的配置。未命中时返回原字符串；命中时返回“原字符串 + 命中的标准名称”。多个知识库对同一简称配置不同标准名称时，全部追加并去重，不阻断检索。

示例：`建工一级怎么办` 处理为 `建工一级怎么办 建筑工程施工总承包一级资质`。匹配采用确定性文本包含判断；较长简称先匹配，并限制配置条数、单项长度和扩展后总长度。原问题始终完整保留。

### 3. 下游只消费统一后的查询文本

统一结果写入检索态的 `RewriteQuery` 与 `KeywordQuery`，发生在向量、ES、SQL、知识图谱、Wiki 和 FAQ 的路由或工具调用之前。下游沿用字符串接口，不新增实体协议，也不重建索引。

不经过普通 RAG 流程的 Agent 知识库工具入口也复用同一预处理能力。Web 搜索不属于知识库范围，不应用知识库简称配置。

### 4. 配置读取失败时退化为原查询

简称扩展是召回增强而不是可用性前提。读取失败时记录日志并继续使用原查询；配置更新通过现有知识库更新事务持久化，新请求重新读取知识库配置，不额外引入缓存。

## Risks / Trade-offs

- [JSON 配置不适合大量映射] → 第一版限制映射数量；确有规模需求时再迁移到独立表。
- [短简称误匹配普通文本] → 限制最小长度、优先长简称，并在 UI 提示使用明确简称。
- [追加多个标准名称使查询变长] → 去重并设置扩展后长度上限，始终保留原查询。
- [不同知识库存在相同简称] → 合并当前授权范围内所有标准名称，让现有排序机制决定相关性。

## Migration Plan

1. 新增可为空且默认 `[]` 的 JSON 配置字段，历史知识库行为不变。
2. 部署后端配置读写和统一预处理，再开放前端配置入口。
3. 回滚应用时忽略该字段即可恢复旧行为；执行 down migration 前按需导出配置。
