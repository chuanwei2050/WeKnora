## Context

租户 CRUD 已有后端路由，但缺少统一状态校验和前端页面；用户仓库已有基础读写方法，但现有 `Register` 会为每个用户新建租户，不能用于租户内开户。认证中间件已经在每个请求中解析用户和租户，适合集中执行禁用状态检查。

## Goals / Non-Goals

**Goals:**

- 建立平台管理员管理租户、平台/租户管理员管理租户内用户的完整闭环。
- 让停用租户、禁用用户、角色变更和密码重置及时作用于后续请求。
- 保证租户管理员无法越权访问其他租户或授予平台级权限。
- 让管理员在统一编辑入口维护用户账号与知识库可见范围，并安全删除没有文档操作记录的普通成员。

**Non-Goals:**

- 不提供公开注册、自助创建租户或用户自助找回密码。
- 不实现复杂组织架构、部门、岗位或自定义角色系统。
- 不硬删除租户关联业务数据；“删除租户”沿用软删除以便数据库一致性和恢复处置。

## Decisions

### 管理 API 采用显式作用域

平台租户 API 使用 `/api/v1/admin/tenants`，租户用户 API 使用 `/api/v1/admin/tenants/:tenant_id/users`。平台管理员可以指定任意租户；租户管理员请求中的 `tenant_id` 必须等于认证上下文租户。相比依赖可被篡改的请求头，显式路径加服务端角色校验更便于审计和测试。

### 租户内开户不复用公开注册

新增专用服务方法，在已存在租户内创建用户并显式设置 `tenant_admin` 或 `member`。租户管理员只能创建 `member`，平台管理员可创建两者；`platform_admin` 只能由平台级管理路径授予且本变更不提供该操作。

管理端开户不收集邮箱。为兼容现有用户表的非空和唯一约束，后端使用新用户 ID 生成仅供内部持久化的唯一占位邮箱；该地址不在用户管理页面展示，也不用于登录或通知。

### 用户资料统一编辑且管理员角色锁定

用户列表不再内联修改角色，用户名、可选新密码、角色和知识库权限统一在编辑弹窗提交。当前角色为 `tenant_admin` 或 `platform_admin` 时角色字段只读，后端同样拒绝角色变更；普通成员可被提升为 `tenant_admin`，提升后角色锁定。用户名保持全局唯一，密码留空表示不重置。

### 知识库可见范围使用显式模式

用户记录增加知识库访问模式 `all | selected` 和选中知识库 ID 列表。默认 `all`，因此当前及未来新增知识库均可见；`selected` 只允许查看、检索和问答所选知识库，空列表表示不可查看任何租户自有知识库。租户管理员和平台管理员始终按 `all` 处理，范围配置仅作用于普通成员。保存 `selected` 时后端校验所有知识库均属于目标租户；知识库列表、详情和检索入口均执行服务端范围校验，不能通过手写 ID 绕过。

### 用户删除以文档引用为安全边界

仅普通成员可删除，当前操作者、租户管理员和平台管理员不可删除。删除前检查用户是否被 `knowledge_bases.created_by`、`knowledges.created_by`、`knowledge_versions.created_by` 或 `knowledge_version_reviews.reviewer_id` 引用；存在任一引用则返回冲突。允许删除时软删除用户并撤销其全部令牌。

### 状态变更集中在认证边界生效

用户 `is_active=false` 或租户 `status=suspended` 时，认证中间件拒绝业务请求。禁用用户、重置密码和角色调整时撤销该用户现有令牌，要求重新登录并获取新权限快照。

### 删除租户使用软删除

删除仅允许平台管理员执行，并使用现有 GORM 软删除。删除前拒绝删除当前平台管理员所在租户，避免把正在操作的管理会话置于不确定状态。软删除租户不级联删除知识、文件或用户。

### 页面复用现有 TDesign 管理模式

新增两个独立路由和表格页面：平台管理员看到“租户管理”，平台/租户管理员看到“用户管理”。页面仅负责可见性和交互，所有权限仍由后端强制执行。

## Risks / Trade-offs

- [角色或状态变更后旧令牌仍带旧声明] → 变更时撤销用户令牌，并由认证中间件每次加载数据库用户状态。
- [软删除后用户名或邮箱唯一约束影响重建] → 租户删除不自动重建同名账号；恢复或数据清理由平台运维显式处理。
- [平台管理员误停用租户] → 停用与删除分离，停用可重新启用；删除操作在 UI 二次确认。
- [管理员角色被误降级后失去管理入口] → 管理员角色创建后锁定，前后端均拒绝修改；仍拒绝禁用最后一个可用租户管理员。
- [仅在前端过滤知识库可被接口绕过] → 在知识库服务与读取边界统一校验用户范围，并覆盖列表、详情和检索测试。
- [删除仍有文档审计引用的用户破坏追溯] → 删除前检查知识库、知识、版本和审核记录中的用户引用。

## Migration Plan

1. 先发布后端管理 API 和认证状态校验。
2. 再发布前端菜单和管理页面。
3. 使用平台管理员创建测试租户与租户管理员，验证隔离后再投入使用。
4. 为用户表增加知识库访问模式和所选知识库 ID 字段，历史用户回填为 `all`。
5. 回滚前端不会影响已有业务；回滚后端时移除新增知识库访问字段，原有用户和知识库数据保持不变。
