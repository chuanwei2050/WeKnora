## Context

知识库当前只有内部 UUID 和名称，Integration API 的 RAG 请求以 `knowledge_base_ids` 指定范围，无法用人工维护的业务编码定位知识库，也不能按文件夹限制检索。文件夹底层是真实知识标签：“未分类”是真实默认标签，“公共文件”是无标签 ID 的虚拟容器，其子文件夹是真实标签并通过 `is_public` 标识。

本变更跨越知识库配置、持久化、Integration API 与检索范围构造，需要确保编码查找不绕过现有授权，并保持未传文件夹筛选时完全兼容现有 RAG 行为。

本变更依赖 `add-public-file-folder` 提供的 `is_public` 标签归属语义；实现时应先完成该变更，或确保等价字段和迁移已存在。

## Goals / Non-Goals

**Goals:**

- 允许管理员在知识库配置中维护可选、租户内唯一的业务编码。
- 允许授权客户端按编码发现可用于筛选的真实文件夹。
- 允许单次和批量 RAG 按多个文件夹过滤，同时自动包含公共子文件夹。
- 对非法编码、冲突、越权和无效文件夹提供稳定且可审计的边界行为。

**Non-Goals:**

- 不用知识库编码替代内部 UUID 或改变现有 `knowledge_base_ids` 必填语义。
- 不允许通过编码跨租户或绕过 client allowlist、用户权限。
- 不改变普通内部知识检索和聊天接口的筛选契约。
- 文件夹列表接口只返回外层普通文件夹，不返回“未分类”、虚拟“公共文件”容器或公共子文件夹。

## Decisions

### 编码作为可空、租户内唯一的业务标识

在知识库表增加可空 `code` 显示字段和不可对外暴露的 `code_key` 规范化字段；空值表示未配置。非空值去除首尾空白后必须匹配 `^[A-Za-z0-9_-]+$`，长度限制为 1–64，`code_key` 使用 ASCII 大写规范化并在同一租户内唯一。系统保留 `code` 的用户输入大小写用于界面显示，但创建、冲突判断和路径查询统一使用 `code_key`，因此 `ABC` 与 `abc` 指向同一业务编码且不能在同一租户并存。

相比全局唯一，租户内唯一与 Integration principal 的租户边界一致，也允许不同租户使用相同业务编码。创建和更新均执行相同校验；清空输入会将编码恢复为未配置。

### 在稳定 Integration API 下按编码列出文件夹

新增 `GET /api/integration/v1/knowledge-bases/by-code/{code}/folders`，同时要求 `kb:list` 和 `knowledge:read` scope。服务端先在 principal 租户内按规范化编码解析知识库，再与 client allowlist 和用户实时权限求交；不存在或无权访问统一返回 `404`，避免泄露知识库存在性。额外的 `knowledge:read` 防止仅能枚举知识库的客户端读取可能包含业务敏感信息的文件夹名称和内部标签 ID。

响应仅包含稳定字段 `id`、`name` 和 `sort_order`。它只返回 `is_public=false` 的外层普通文件夹，并排除名为“未分类”的默认标签；虚拟“公共文件”及 `is_public=true` 的公共子文件夹均不返回。结果按 `sort_order` 稳定排序。

### 用可选 folder_ids 表达 RAG 文件夹范围

`POST /api/integration/v1/rag/search` 增加可选 `folder_ids`；批量接口的每个 query 增加同名字段。字段缺失、`null` 或空数组都表示不启用文件夹过滤，保持当前检索全部标签的行为。

字段为非空数组时，服务端在执行检索前校验 ID 非空、无重复、数量不超过配置上限，并确认每个 ID 都是本次 `knowledge_base_ids` 范围内的真实、非“未分类”标签。随后查询这些知识库的全部 `is_public=true` 标签，将其与显式 ID 去重合并为最终 `tag_ids`。因此调用方即使只选择普通文件夹，也始终能检索公共子文件夹；显式选择公共子文件夹不会产生重复条件。

当同一单次查询或批量子查询同时提供非空 `knowledge_ids` 与非空 `folder_ids` 时，两者 MUST 取交集：服务端在检索前确认每个显式文档都属于最终 `tag_ids`，任一文档在范围外则整次返回 `400 invalid_knowledge_folder_scope`。直接 Chunk 加载路径也必须接收并执行相同的最终标签范围校验，不能因指定文档而绕过文件夹限制。

### 在检索入口一次性构造最终范围

Integration handler/service 负责授权和文件夹范围解析，然后把最终 `tag_ids` 传给检索层。底层检索器只消费已经验证的标签集合，不自行查找公共文件夹，从而让单次与批量请求复用同一范围解析逻辑，并确保向量、关键词及混合检索使用完全相同的过滤条件。

文件夹筛选作用于所有请求中的知识库：显式 ID 可以来自任一所选知识库，自动公共集合也来自每个所选知识库。任一显式 ID 不属于所选知识库范围时整次返回 `400 invalid_folder_ids`，不执行部分检索。

## Risks / Trade-offs

- [编码大小写容易被人工混淆] → 保留原始显示值，但用统一大写 `code_key` 查找和判重，并在 UI/API 文档声明大小写不敏感。
- [并发写入同一规范化编码绕过预检查] → 对 `(tenant_id, code_key)` 使用数据库唯一索引并把约束错误映射为稳定 `409 knowledge_base_code_conflict`。
- [公共子文件夹较多导致过滤集合膨胀] → 对最终去重后的 `tag_ids` 设置服务端硬上限；超限时返回稳定参数错误而不是静默截断。
- [不同检索引擎对标签过滤支持不一致] → 在统一检索请求模型中增加标签范围，并对所有启用的 retriever driver 做契约测试。
- [按编码返回 404 难以区分不存在和无权限] → 这是防止资源枚举的有意取舍，拒绝原因仍写入内部审计。

## Migration Plan

1. 为知识库表增加可空 `code` 和 `code_key` 字段及 `(tenant_id, code_key)` 唯一索引；存量知识库两字段保持 `NULL`，无需回填。
2. 上线知识库创建、更新、查询和配置界面支持，再上线 Integration 文件夹列表接口。
3. 在所有检索驱动具备 `tag_ids` 过滤能力后，开放单次与批量 RAG 的 `folder_ids` 字段。
4. 回滚 API 时可保留未使用的 `code` 字段；删除字段前需先移除唯一索引，存量业务编码会丢失，因此数据库回滚仅用于明确接受数据损失的回退。
